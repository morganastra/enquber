# Packaging for Windows

Enquber cross-compiles for 64-bit Windows from Linux with MinGW-w64 and
produces the following artifacts in `build/windows`:

    enquber.exe                         the bare binary
    enquber-<version>-win64.zip         a folder to unzip and run
    enquber-<version>-win64-setup.exe   the NSIS installer
    enquber-<version>-win64.msix        the MSIX package for the Store

The `just` tasks for Windows cross-compilation and packaging:

    just mingw-sdk           fetch the target Qt 6 and libqrencode (MSYS2 tree)
    just build-windows       cross-compile the application
    just run-wine         deploy the runtime and run it under Wine
    just package-windows     deploy + zip
    just installer-windows   deploy + zip + build the NSIS setup
    just msix-windows        deploy + zip + build the MSIX package

## Dependencies

Cross-compilation requires a working native compilation environment
plus many additional dependencies!

First, mingw and wine; get them from the Arch repos

    sudo pacman -Syu mingw-w64-gcc wine

### The MinGW Qt/libqrencode SDK

Next we need Qt 6 and libqrencode for Windows. The cross build takes
them from an extracted MSYS2 tree. This is automated by
`packaging/windows/mingw-sdk.py` and wrapped by the `just` task:

    just mingw-sdk

This downloads and extracts `mingw-w64-x86_64-qt6-base` and
`mingw-w64-x86_64-qrencode` and their runtime dependencies from the
MSYS2 repository database.

Set `ENQUBER_MINGW_PREFIX` (default `~/.local/msys2-mingw64`) to
control where they are extracted.

### NSIS

`makensis` is packaged by some linux distributions but not Arch.
Get the Debian packages:

    http://deb.debian.org/debian/pool/main/n/nsis/nsis_3.12-1_amd64.deb
    http://deb.debian.org/debian/pool/main/n/nsis/nsis-common_3.12-1_all.deb

Extract them into `~/.local/opt/nsis` and create a wrapper script
`~/.local/bin/makensis`:

    #!/bin/sh
    NSISDIR="${NSISDIR:-$HOME/.local/opt/nsis/usr/share/nsis}"
    export NSISDIR
    exec "$HOME/.local/opt/nsis/usr/bin/makensis" "$@"

### MSIX (makemsix)

`--msix` / `just msix-windows` need `makemsix` from Microsoft's MSIX SDK,
Build it once from source:

    git clone https://github.com/microsoft/msix-packaging
    cd msix-packaging
    ./makelinux.sh -sb --pack --skip-samples --skip-tests
    .vs/bin/makemsix    # that is the tool; --makemsix PATH points at it

`makemsix` is linked against the `libmsix.so` in `.vs/lib`, so run it from the
checkout or put a wrapper that sets `LD_LIBRARY_PATH` on PATH. If the build
fails in the bundled xerces against the current ICU headers, raise the pinned
`CMAKE_CXX_STANDARD` from 14 to 17 in `CMakeLists.txt` and
`lib/xerces/CMakeLists.txt`.

## Cross-compiling

    just build-windows

This configures the `windows` preset from `CMakePresets.json`, which uses
`cmake/toolchain-mingw-w64.cmake`: the MinGW-w64 compilers, the SDK tree as
`CMAKE_FIND_ROOT_PATH` (Qt 6 and libqrencode are found there) and the native
Qt as `QT_HOST_PATH` for the translation tools. This builds
`build/windows/enquber.exe`.

`packaging/windows/wine-run.py` copies the executable to `build/windows/deploy`, runs
`windeployqt` (under Wine) to copy the Qt runtime and plugins, walks
the PE import table for the remaining MinGW and third-party DLLs, and starts
it in a dedicated Wine prefix (`~/.local/share/wineprefixes/enquber`).  See
`--help` for the flags. For short:

    just run-wine

Two things to know when debugging under Wine:

- Wine drops plain `QT_*` environment variables; pass Qt settings as
  `WINEQT_...` instead, e.g.
  `WINEQT_FORCE_STDERR_LOGGING=1 WINEQT_LOGGING_RULES="enquber.dnd.debug=true"`.
- Drag and drop only works between Wine windows - dragging from the
  window in Wine to a Linux native window or vice versa will not work.

## Building the packages

    just package-windows      # the zip
    just installer-windows    # the zip and the NSIS setup
    just msix-windows         # the zip and the MSIX package

All three recipes build and deploy first, then call
`packaging/windows/package-windows.py`.

That tool reads the version from `build/windows/CMakeCache.txt`, writes
`enquber-<version>-win64.zip` with a versioned top-level folder, and with
`--installer` also runs `makensis` on `packaging/windows/enquber.nsi` to
produce `enquber-<version>-win64-setup.exe` (about 23 MB, LZMA-compressed from
the 80 MB tree).  `--makensis PATH` picks a specific makensis; `--msix` builds
the Store package described below.

### NSIS installer

`packaging/windows/enquber.nsi` is a Modern UI installer that installs
per user below `%LOCALAPPDATA%\Programs\Enquber`. It creates Start menu
shortcuts and, optionally, a desktop shortcut, plus an entry in
Settings > Apps.

It supports unattended use: `setup.exe /S` and `uninstall.exe /S`.

The icon and bitmaps are generated by `tools/generate-icon.py`.

#### Code signing

The setup executable is unsigned, so downloads from the internet trigger
SmartScreen's "Windows protected your PC" (the user can still choose "More
info > Run anyway"). For testing you can also get around this by fetching
the file with `curl` which does not add the Mark-of-the-Web.

### MSIX package

`--msix` stages the deployed tree with `packaging/windows/AppxManifest.xml.in`
and the tile logos from `data/icon/msix`, then packs it with `makemsix` into
`enquber-<version>-win64.msix`.

#### Signing the MSIX for sideload testing

A sideloaded MSIX package has to be self-signed and the target machine
has to be configured to trust the certificate.

Even though a valid MSIX package can be created on Linux it can
apparently only be signed on Windows. Wine's `signtool` does not work.

We can get `signtool` from the `Microsoft.Windows.SDK.BuildTools`
NuGet package (a `.nupkg` is a zip archive). In the guest machine:

    V=10.0.22621.3233
    U=https://api.nuget.org/v3-flatcontainer/microsoft.windows.sdk.buildtools
    curl -LO "$U/$V/microsoft.windows.sdk.buildtools.$V.nupkg"
    unzip microsoft.windows.sdk.buildtools.$V.nupkg 'bin/*/x64/*' -d sdkbt
    sdkbt/bin/*/x64/signtool.exe

Mint a self-signed code-signing certificate whose subject is the manifest's
`Identity/@Publisher` (`CN=Enquber` by default)

On Linux:

    openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
        -keyout key.pem -out cert.pem -subj '/CN=Enquber' \
        -addext 'keyUsage=critical,digitalSignature' \
        -addext 'extendedKeyUsage=critical,codeSigning' \
        -addext 'basicConstraints=critical,CA:false'
    openssl pkcs12 -export -out enquber.pfx -inkey key.pem -in cert.pem \
        -passout pass:enquber
    openssl x509 -in cert.pem -outform DER -out enquber.cer

Then in the guest (the certificate import needs an elevated shell):

    Import-Certificate -FilePath enquber.cer -CertStoreLocation Cert:\LocalMachine\TrustedPeople
    signtool.exe sign /fd SHA256 /a /f enquber.pfx /p enquber enquber-<version>-win64.msix
    Add-AppxPackage -Path enquber-<version>-win64.msix

After that the app is a normal package:

    Get-AppxPackage Enquber                       # PackageFamilyName, InstallLocation
    explorer.exe shell:AppsFolder\<PFN>!Enquber   # launch; the AppId is from the manifest

## Testing on Windows

Wine is fine for smoke checks, but packaging should be verified on a real
Windows installation. A VirtualBox VM can be set up:

    VBoxManage createvm --name Win10-Enquber --ostype Windows10_64 --register
    VBoxManage modifyvm Win10-Enquber --memory 6144 --cpus 4 --vram 128 \
        --graphicscontroller vboxsvga --nic1 nat --boot1 dvd --boot2 disk
    VBoxManage createmedium disk --format VDI --size 65536 \
        --filename "$HOME/VirtualBox VMs/Win10-Enquber/Win10-Enquber.vdi"
    VBoxManage storagectl Win10-Enquber --name SATA --add sata --controller IntelAhci --bootable on
    VBoxManage storageattach Win10-Enquber --storagectl SATA --port 0 --type hdd \
        --medium "$HOME/VirtualBox VMs/Win10-Enquber/Win10-Enquber.vdi"
    VBoxManage unattended detect --iso=/path/to/Win10_22H2.iso   # lists image indexes
    VBoxManage unattended install Win10-Enquber --iso=/path/to/Win10_22H2.iso \
        --user=enquber --password=enquber --full-user-name=Enquber \
        --hostname=enquber-vm.local --locale=en_US --country=US --time-zone=UTC \
        --image-index=6 --no-install-additions --start-vm=headless

Get the setup executable into the guest over the NAT address:

    cd build/windows && python3 -m http.server 8000

Then inside the guest:

    curl -o %USERPROFILE%\Desktop\enquber-setup.exe ^
        http://10.0.2.2:8000/enquber-<version>-win64-setup.exe

It's possible to programmatically drive the guest with
`VBoxManage controlvm keyboardputstring`/`keyboardputscancode`.
Take screenshots with `VBoxManage controlvm ... screenshotpng`.

## Troubleshooting

- `No Qt 6 below <prefix>/mingw64` - fetch the SDK with `just mingw-sdk`, or
  point `ENQUBER_MINGW_PREFIX` at an existing tree.
- `error: makensis not found` - install NSIS (see above) or pass
  `--makensis PATH`.
- The installer stops with "Enquber appears to be running" - close the
  application (or run `taskkill /IM enquber.exe /F`) and click Retry.
- `windeployqt` prints `MESA-EGL`/`DRI3` warnings under Wine; they can be
  ignored.
